# PSGA Independent Verification — RideShareEU

**Scope:** verifying that the Priority-Scored Greedy Algorithm (PSGA) scoring formula, as implemented in production (`server/services/psgaService.js` + `server/config/psgaConfig.js`), is correctly reproduced by a second, independently-written implementation — not a review of match *quality* or *ranking effectiveness* (that's `validation/score_against_ground_truth.py`'s job, against human-labelled ground truth).

**Method:** the production formula was read directly from source and restated as an exact specification (weights, gating thresholds, component formulas — see below). A second implementation, [validation/psga_independent_recheck.py](../../validation/psga_independent_recheck.py), was then written from that specification without copying any code from the existing thesis-formula reference module (`validation/psga.py`), so agreement between the two is a meaningful check rather than a module compared against itself. Both were run against the same 500-row synthetic dataset (`validation/dataset_500_pairs.json`, generated by `validation/generate_dataset.py`) and every field diffed row-by-row.

---

## The production formula (source of truth)

```
Score = w1·RouteOverlap + w2·ScheduleAlignment + w3·PreferenceMatch
```

- **Weights** ([psgaConfig.js:2](../../server/config/psgaConfig.js#L2)): `w1=0.5, w2=0.3, w3=0.2`.
- **Stage 1 hard gate** (candidate dropped, never scored, if either fails): `RouteOverlap ≥ minRouteOverlap` (`0.4`) and `timeDiff ≤ flexWindow` (passenger's own, default `15` min).
- **RouteOverlap** ([psgaService.js:74-93](../../server/services/psgaService.js#L74-L93)): fraction of 21 sampled points along the passenger's straight origin→destination line that fall within `corridorMeters` (`1500`) of the host's route polyline (`trip.routeWaypoints`, Mapbox Directions geometry fetched client-side at trip creation, falling back to a 2-point straight line if absent).
- **ScheduleAlignment** ([psgaService.js:95-98](../../server/services/psgaService.js#L95-L98)): linear decay, `max(0, 1 - timeDiff/flexWindow)`.
- **PreferenceMatch** ([psgaService.js:115-120](../../server/services/psgaService.js#L115-L120)): binary — seats available, host's `SAME_GENDER` preference satisfied, familiar-riders-only satisfied. The passenger's *own* same-gender-only preference is enforced separately, as a hard pre-filter on the candidate pool one layer up in [matchController.js:111-123](../../server/controllers/matchController.js#L111-L123), before any trip reaches the scoring function at all.

| Field | Disagreements | Rate |

This is a byte-for-byte agreement across all 500 synthetic (passenger, trip) pairs, on every scored component, confirming the production formula's scoring logic is correctly and reproducibly specified — a second, independent implementation of the same stated formula produces identical output.

## A real drift bug was found and fixed during this process

The first attempt at this independent recheck did **not** agree cleanly — it disagreed on 104/500 rows (93 on `routeOverlap`, 17 on `preferenceMatch`, both rolling into `score`). Rather than tuning the recheck script until it silently agreed, both disagreements were root-caused against source before anything was called "verified":

**1. `routeOverlap` (93/104 rows) — a stale constant in the frozen thesis-formula reference module, not a bug in production or in the dataset export.**

`dataset_500_pairs.json`'s ground-truth scores are generated by `validation/psga.py`, a standalone Python reference implementation of the thesis proposal's stated formula (Section 5.1.2.5) — deliberately independent of the live app's routing/HTTP stack. That module's `CORRIDOR_METERS` was hardcoded at `500`, left over from *before* `psgaConfig.js`'s `corridorMeters` was widened to `1500` in a later change ("Task 25") to absorb free-tier geocoding drift (Nominatim commonly resolving a typed address 1-2km off). `validation/psga.py`'s own comment claimed its constants "match `server/config/psgaConfig.js`" — that claim had gone stale without the value being updated to follow it. A 3x-wider corridor swallowing nearby sampled points into full overlap produced exactly the observed pattern: the recheck's `routeOverlap` (computed at the current production value, 1500) was always ≥ the dataset's baked-in value (computed at the stale 500), pinning at `1.0000` regardless of the dataset's `0.40`–`0.95` range.

**Fix:** `validation/psga.py`'s `CORRIDOR_METERS` was corrected from `500` to `1500`, its comment made self-documenting about the sync requirement (states explicitly it must match `psgaConfig.js`'s `corridorMeters`, with a last-synced date), and `dataset_500_pairs.json` was regenerated from the corrected module. All other shared constants (`MIN_OVERLAP`/`minRouteOverlap` = 0.4, `DEFAULT_FLEX_WINDOW`/`defaultFlexWindowMinutes` = 15, `W1/W2/W3`/`weights.w1/w2/w3` = 0.5/0.3/0.2) were re-checked against `psgaConfig.js` and confirmed already in sync — no other drift found. (`destinationAnchorMeters` exists only in `psgaConfig.js`, for the "Show All" empty-state fallback; `validation/psga.py` doesn't implement that code path, so there is nothing to sync there — not a gap.)

**2. `preferenceMatch` (17/104 rows) — a real gap in the recheck script itself, not in production or in `validation/psga.py`.**

The first draft of the recheck script mirrored `psgaService.js`'s `checkPreferenceMatch` alone, which checks only the *host's* gender preference — correct for that function in isolation, but incomplete as a stand-in for the full production pipeline, since the *passenger's* own same-gender-only preference is enforced separately, upstream, as a candidate-pool pre-filter (see "PreferenceMatch" above). `validation/psga.py`'s `preference_match()` bakes both directions into one function, matching the thesis's stated design ("checked both directions"). The recheck script was missing the passenger-side check entirely, so a passenger who required a same-gender host and got a mismatched one was correctly failed by the dataset (`preferenceMatch: 0`) but incorrectly passed by the recheck (`True`).

**Fix:** the recheck script's `preference_match()` was corrected to check both directions, matching `validation/psga.py` and the thesis's stated design.

Both fixes were verified independently — the dataset was regenerated and the recheck re-run, producing the clean 500/500 result above — rather than assumed to have worked.

## Open item, not resolved here: a discrepancy with the written thesis proposal

The thesis proposal document itself ([docs/thesis/thesis-proposal.md:1053](../../docs/thesis/thesis-proposal.md)) states: *"Overlap is computed as the fraction of the Passenger route that falls within a **500-meter** corridor of the host route."* The corridor was widened to 1500m in the live application after that text was written, for a specific, documented production reason (geocoding drift). This verification deliberately targeted the *current production value* (1500m), per this task's own framing ("independently verified against the actual production formula"), not the value written in the proposal. That means the proposal text and the shipped system now describe two different corridor widths. This is a real, outstanding discrepancy worth resolving explicitly in the final manuscript (either an addendum noting the post-proposal change and its rationale, or a decision to revert production to 500m) — it was not silently reconciled as part of this fix, since changing the formal proposal text is a decision for the thesis author/advisor, not something to resolve unilaterally here.
